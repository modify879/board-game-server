## 동시성

### 게임 상태는 단일 실행기, 돈은 비관적 락인 이유
게임 상태(홀덤 테이블·핸드)는 초당 여러 번 바뀌므로 테이블별 단일 실행기(`TableExecutor`)로 직렬화한다.
지갑·충전·환전 요청은 드물지만 정확히 한 번만 반영돼야 하는 돈이라 비관적 락으로 직렬화한다.

`@Version` 을 걷어낸 이유: 이중 승인·이중 지급처럼 한쪽은 반드시 성공해야 하는 경로에서 낙관적 락은
실패만 돌려줄 뿐이다. 비관적 락은 두 번째 호출이 이미 바뀐 상태를 보고 기존 도메인 예외로 떨어진다.

둘 다 **서버 한 대를 전제**한다. 여러 대로 가면 샤딩과 펜싱 토큰이 필요해진다.

### 타이머는 상대 시간, 벽시계는 "언제 일어났나" 기록에만
WSL2 호스트의 벽시계가 주기적으로(약 30초마다) 뒤로 튄다(`journald: Time jumped backwards`).
예약 시각(벽시계 `Instant`)을 발화 시점에 다시 비교하는 방식은 그 순간 비교가 실패해 재무장 없이
조용히 끝나버렸다(홀덤 다음 핸드 카운트다운에서 실제로 겪었다). 벽시계는 "이 일이 언제 일어났는가"를
기록하는 데만 쓴다 — JWT 의 `exp`/`iat`, 원장 타임스탬프, TTL 같은 것들이다.

### 호출자 타임아웃 대신 DB 에서 상한을 두는 이유
Akka/Pekko·Orleans·Erlang 모두 호출자만 타임아웃하고 처리자는 취소하지 않는다 — 처리는 늦게 커밋될 수 있다.
그래서 `TableExecutor.call` 의 `future.get()` 에 타임아웃을 걸면 **클라이언트에 실패를 알린 뒤에 돈이 옮겨질 수 있다.**
실제로 멈추는 곳은 DB 대기(지갑 행 락)뿐이므로 `lock_timeout`·`statement_timeout` 으로 작업 자체를 끊는다.
실패한 타이머 작업은 버리지 않고 재시도하고, 끝내 안 되면 핸드를 취소하고 환불한다.

### 턴 만료 폴드의 환불을 기립과 같은 트랜잭션에 두는 이유
환불은 기립과 **원자적이어야** 한다 — 좌석만 비고 돈이 안 가면 칩이 사라진다. 실패는 재시도로 흡수한다.

### 테이블을 지우지 않고 닫는 이유
원장의 `GAME_TABLE` 참조와 앞으로의 핸드 히스토리가 테이블 이름을 찾을 수 있어야 한다. 행을 지우면 둘 다 고아가 된다.
닫힘은 저장소 어댑터 한 곳에서 "없음" 으로 걸러 내므로 명령·조회 경로가 닫힘을 따로 알 필요가 없다.

### 테이블별 인메모리 상태를 주인이 `TableClosed` 로 치우는 이유
정리 담당 한 곳이 모든 컴포넌트를 대신 부르면 한 줄이 빠져도 테스트가 모르고, 하나가 던지면 나머지를 건너뛴다.
AFTER_COMMIT 리스너는 afterCompletion 에서 각자 돌아 실패가 서로 번지지 않는다. 키를 `TableId` 로 통일하고
스캔 테스트(`TableClosedListenersTest`)가 리스너를 강제한다 — Long 키는 스캔에 안 보이므로 규칙으로 막는다.
