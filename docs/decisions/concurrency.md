## 동시성

### 게임 상태는 단일 실행기, 돈은 비관적 락인 이유
게임 상태(홀덤 테이블·핸드)는 초당 여러 번 바뀌므로 테이블별 단일 실행기(`TableExecutor`)로 직렬화한다.
지갑·충전·환전 요청은 드물지만 정확히 한 번만 반영돼야 하는 돈이라 비관적 락으로 직렬화한다.

`@Version` 을 걷어낸 이유: 이중 승인·이중 지급처럼 한쪽은 반드시 성공해야 하는 경로에서 낙관적 락은
실패만 돌려줄 뿐이다. 비관적 락은 두 번째 호출이 이미 바뀐 상태를 보고 기존 도메인 예외로 떨어진다.

둘 다 **서버 한 대를 전제**한다. 여러 대로 가면 샤딩과 펜싱 토큰이 필요해진다.

### 회원 탈퇴를 지갑 락으로 직렬화하는 이유
탈퇴의 "좌석 없음·지갑 비었음" 확인과 대기열 착석(바이인)이 엇갈리면 앉은 채 탈퇴된다. 둘이 공통으로 지나는 곳은 지갑 행뿐이라 거기서 줄 세운다.
탈퇴는 한 트랜잭션에서 지갑을 먼저 잠그고 좌석을 본다. 바이인·충전·환전 요청·관리자 조정은 지갑을 잠근 뒤 활성 여부를 본다.
착석이 먼저 커밋됐으면 탈퇴가 좌석을 보고 거절하고, 탈퇴가 먼저 락을 잡았으면 착석이 기다렸다가 탈퇴 상태를 보고 떨어진다.
탈퇴와 돈 경로의 직렬화에는 사용자 행 락을 쓰지 않는다 — 돈이 움직이는 모든 경로가 이미 지갑 락을 잡으므로 거기서 줄 세우면 된다.
탈퇴도 사용자 행을 잠그지만(아래) 그것은 사용자 행 자체의 갱신 손실을 막기 위해서이고, 지갑 락 **뒤에** 잡는다.

### 사용자 행도 비관적 락
사용자를 바꾸는 명령(로그인 실패 잠금·비밀번호·닉네임·프로필 이미지·역할·잠금 해제·탈퇴)은 모두 "읽고 → 도메인 객체를 고치고 →
행 전체를 저장" 한다. 버전도 락도 없을 때는 같은 사용자에 대한 두 명령이 겹치면 나중 저장이 앞의 변경을 조용히 되돌렸다 —
로그인 실패 잠금이 방금 바꾼 비밀번호 해시를 되돌리고, 닉네임 변경이 탈퇴의 `withdrawn_at` 을 지워 계정을 되살렸다.
그래서 이 명령들은 짧은 트랜잭션 하나에서 `findByIdForUpdate`(행 락) → 변경 → `save` 를 한다. 해싱·Redis·파일은 트랜잭션 밖이다.

`@Version` 이 아니라 비관적 락인 이유:
- 모두 한 요청 안에서 끝나는 읽기-고치기-쓰기다. 클라이언트가 본 상태를 근거로 한 편집이 아니라서 두 번째 호출에 실패를 돌려줄 이유가 없다 —
  기다렸다가 바뀐 상태를 보고 기존 도메인 예외(`USER_NOT_FOUND`·`ACCOUNT_LOCKED`·`CURRENT_PASSWORD_MISMATCH`)로 떨어지거나 그대로 성공하면 된다.
  새 에러 코드도, 재시도 루프도 생기지 않는다
- 한 사용자의 행을 동시에 고치는 일은 드물어 락 대기가 거의 없다
- 돈과 같은 방식이라 "두 번째 호출은 바뀐 상태를 본다" 는 한 가지 모델로 읽힌다

Postgres 는 `FOR UPDATE` 와 `FOR NO KEY UPDATE` 를 구분한다. 지갑·좌석 INSERT 의 FK 검사는 부모(`users`) 행에 `FOR KEY SHARE` 를 잡는데
`FOR UPDATE` 와는 충돌하고 `FOR NO KEY UPDATE` 와는 충돌하지 않는다. Hibernate 7.4.5 의 `PostgreSQLDialect` 는 `PESSIMISTIC_WRITE` 를
`for no key update` 로 내보내므로 사용자 행 락이 같은 사용자의 지갑 생성·착석을 막지 않는다(`UserRepositoryAdapterIntegrationTest` 가
락을 쥔 채 지갑 INSERT 가 끝나는지로 못 박는다 — 방언이 바뀌면 거기서 깨진다). 단 유니크 인덱스 컬럼(닉네임)을 실제로 바꾸는 UPDATE 는
그 자체로 강한 행 락이 되므로 잠금 순서는 여전히 지갑 → 사용자 행이다.

낙관적 락(`@Version`)이 맞아지는 때: 여러 HTTP 요청에 걸친 편집 — 클라이언트가 화면에 띄운 상태를 근거로 고쳐 보내는 관리자 편집 화면 같은 것.
그때는 서버가 그사이의 변경을 덮어쓰지 말고 충돌을 알려야 하므로 버전을 왕복시킨다.

### 타이머는 상대 시간, 벽시계는 "언제 일어났나" 기록에만
WSL2 호스트의 벽시계가 주기적으로(약 30초마다) 뒤로 튄다(`journald: Time jumped backwards`).
예약 시각(벽시계 `Instant`)을 발화 시점에 다시 비교하는 방식은 그 순간 비교가 실패해 재무장 없이
조용히 끝나버렸다(홀덤 다음 핸드 카운트다운에서 실제로 겪었다). 벽시계는 "이 일이 언제 일어났는가"를
기록하는 데만 쓴다 — JWT 의 `exp`/`iat`, 원장 타임스탬프, TTL 같은 것들이다.
수용한 예외가 하나 있다 — `IdleTableSweeper` 는 주기 스윕마다 벽시계 `emptySince` 와 현재 시각을 비교한다. 시계가 뒤로 튀면 닫기가 다음 스윕 이후로 미뤄질 뿐 재무장이 사라지는 일은 없다(스윕이 주기적으로 다시 돈다).

### 호출자 타임아웃 대신 DB 에서 상한을 두는 이유
Akka/Pekko·Orleans·Erlang 모두 호출자만 타임아웃하고 처리자는 취소하지 않는다 — 처리는 늦게 커밋될 수 있다.
그래서 `TableExecutor.call` 의 `future.get()` 에 타임아웃을 걸면 **클라이언트에 실패를 알린 뒤에 돈이 옮겨질 수 있다.**
실제로 멈추는 곳은 DB 대기(지갑 행 락)뿐이므로 `lock_timeout`·`statement_timeout` 으로 작업 자체를 끊는다.
실패한 타이머 작업은 버리지 않고 재시도하고, 끝내 안 되면 핸드를 취소하고 환불한다.

### 턴 만료 폴드의 환불을 기립과 같은 트랜잭션에 두는 이유
환불은 기립과 **원자적이어야** 한다 — 좌석만 비고 돈이 안 가면 칩이 사라진다. 실패는 재시도로 흡수한다.

### 테이블을 지우지 않고 닫는 이유
원장의 `GAME_TABLE` 참조와 앞으로의 핸드 히스토리가 테이블 이름을 찾을 수 있어야 한다. 행을 지우면 둘 다 고아가 된다.
닫힘은 명령 저장소 어댑터와 조회 어댑터(`HoldemTableQueryRepositoryAdapter`)가 각자 `closedAt` 으로 "없음" 처리하므로 명령·조회 서비스가 닫힘을 따로 알 필요가 없다.

### 테이블별 인메모리 상태를 주인이 `TableClosed` 로 치우는 이유
정리 담당 한 곳이 모든 컴포넌트를 대신 부르면 한 줄이 빠져도 테스트가 모르고, 하나가 던지면 나머지를 건너뛴다.
AFTER_COMMIT 리스너는 afterCompletion 에서 각자 돌아 실패가 서로 번지지 않는다. 키를 `TableId` 로 통일하고
스캔 테스트(`TableClosedListenersTest`)가 리스너를 강제한다 — Long 키는 스캔에 안 보이므로 규칙으로 막는다.
